The problem statement

A solo founder's Friday chore

The idea: ShipLog — a founder enters their public GitHub username and gets a draft weekly "build in public" update, generated from real commits, merged PRs, and releases over the last 7 days. They review and edit it before anything goes anywhere. It never posts on their behalf.

The belief: solo founders who build in public lose real time every week doing the same manual chore — reconstructing what they actually shipped from their own commit history, then writing it up. The reconstruction step, not the writing, is what a tool could remove — as long as the founder still controls what comes out the other end.

Why now, honestly: mostly founder intuition, not evidence yet — the hypothesis says so explicitly. GitHub's public API makes the data reachable without auth, and "build in public" is a common habit, but neither confirms the chore is painful enough, or that founders would trust a machine-drafted first pass. That's what discovery exists to find out before any of it becomes a spec.

The interviews

Four conversations, two roles, one real contradiction

Keel derived six assumptions the idea depends on, then a non-leading interview guide. Four interviews later, the gate had what it needed — and one belief didn't survive contact with the evidence.

The artifacts

Brief, constitution, spec — one traceable chain

What the evidence ruled out: a draft based on raw GitHub activity alone, presented as sufficient. Two independent sources called that output a changelog, not an update.

What shipped instead: activity grouped by repo, paired with a founder-editable "why" field woven into the draft, and a review step that's structurally mandatory — three independent founders were unconditional on that point.

What converge actually caught

Copy and Export were reachable with an empty draft — before the first Generate, or after a failed lookup, both buttons were clickable and would silently act on nothing. Not a security issue, but a real crack in "mandatory review" — there was nothing to review. Fixed as task T035: both buttons now stay disabled until the draft has content. This is the pipeline's own safety net working, not a bug found from outside it.

Field notes

What running this for real actually found

The point of this run was to find out if the documented flow holds up, not to make something look finished. Reported plainly, findings included.

doc gap

The site says /speckit.keel.guide. Reality says /speckit-keel-guide.

Current Spec Kit CLI installs Claude Code Skills (.claude/skills/*/SKILL.md, dash-invoked), not the dot-separated Commands earlier docs assumed. The extension still installs and works correctly — only the invocation syntax was stale.

doc gap

"Verify it installed cleanly" doesn't work as written.

./tests/test-install.sh is deliberately stripped from what ships into a consumer project by .extensionignore — a maintainer check meant to run against the source repo, where it passed 39/39. It simply doesn't exist at the path the install instructions point to after a real specify extension add.

design risk

The gate only enforces if someone remembers to run it.

before_plan and after_implement are registered as optional hooks, which this branch's skill files only surface, never auto-execute. Nothing stopped this run from going straight from a bare /speckit-plan to /speckit-implement without ever touching keel-gate.sh — it only enforced here because the run was disciplined to check by hand at each stage.

real bug, caught

GitHub's actual API payload doesn't match commonly-remembered docs.

PushEvent.payload on the real public events feed carries no commit-message array at all; a merged PR's title/URL/state are all null on the event itself. Written from memory instead of curled first, this would have shipped silently — commits with no messages, PRs with no titles. Caught by checking the live API before writing the parser, not after.

real limit, hit twice

60 requests/hour/IP is a real ceiling, not a footnote.

Unauthenticated GitHub API access — the whole point of "no auth token required" — genuinely exhausted twice during this run, once from ordinary verification traffic. One digest for a prolific user alone can spend 40+ calls. The app degrades gracefully (a plain rate-limit message, not a crash), but the ceiling is real and low.

held up

The gate script itself has no bugs.

39/39 of its own tests pass, including parser edge cases (a literal | inside a statement, a supported row with an empty evidence column). Run here against a real multi-assumption scenario with a genuine contradiction and supersession, it computed every number correctly and blocked/passed exactly when it should have.
